# US-102 (AIH-102) — URL shortener API

Priority: High · Status: Draft for review · Target stack: Python 3.12 + FastAPI, pytest + httpx/TestClient

## Overview

A marketer needs to turn a long URL into a short link that is easy to share, and to see how many times each short link was used. This release delivers a small JSON HTTP API with three operations:

- create a short link for a long URL,
- resolve a short link by redirecting the caller to the long URL,
- read the click count for a short link.

Links are stored in memory for the lifetime of the process. Invalid URLs are rejected and never stored. There is no user interface and no authentication in this release (see Open Questions OQ-011, OQ-012).

Scope is limited to the three endpoints in this document plus an operational health check. Listing, editing, deleting, custom aliases, expiry and accounts are out of scope unless an Open Question is resolved otherwise.

## Actors

| Actor | Description | Interactions |
|---|---|---|
| Marketer (API consumer) | Human or marketing tool that creates short links and reads their statistics. | `POST /links`, `GET /links/{code}/stats` |
| Link visitor (end user) | Anyone who opens a short link, typically from a browser or social app. | `GET /{code}` |
| Operator | Runs and monitors the service; uses the health endpoint and logs. | `GET /health` |
| Automated test suite | pytest tests using httpx/TestClient that exercise every acceptance criterion. | All endpoints |

## User Stories

- **US-102** (this story, High): As a marketer I want short links so that long URLs are easy to share.
- **US-102.1** (derived): As a marketer I want invalid URLs rejected so that I never share a broken short link.
- **US-102.2** (derived): As a marketer I want to read the click count of a short link so that I can judge which links perform.
- **US-102.3** (derived, operational): As an operator I want a health check so that I can confirm the service is up.

## Functional Requirements

### FR-001 — Create a short link
`POST /links` accepts a JSON body with a single field `url` (string) and returns a new short link.
- Acceptance criteria:
  - A valid request returns HTTP `201`.
  - The response body is JSON with `code` (string, non-empty), `long_url` (the stored URL), `short_url` (absolute URL consisting of the configured base URL plus `code`), and `created_at` (ISO-8601 UTC timestamp).
  - The `code` returned is immediately resolvable through `GET /{code}`.
  - A `Content-Type` other than `application/json` is rejected with HTTP `415` and no link is created.
  - Malformed JSON or a missing/blank `url` field returns HTTP `422` (FastAPI validation) or `400`, using the FR-009 error envelope, and no link is created.

### FR-002 — URL validation
Only absolute `http` or `https` URLs with a non-empty host are accepted.
- Acceptance criteria:
  - `http://example.com/a/very/long/path?x=1` is accepted.
  - `https://example.com` (no path) is accepted.
  - Each of the following is rejected with HTTP `400`, `error.code = "invalid_url"`, and is not stored: missing scheme (`example.com`), unsupported scheme (`ftp://`, `javascript:`, `data:`, `mailto:`), host-less value (`http:///path`, `http://`), strings with leading/trailing whitespace, strings containing ASCII control characters, and values longer than 2048 characters.
  - A rejected request does not consume a code and does not appear in statistics.
  - Validation is case-insensitive for scheme and host but the URL is stored exactly as submitted (no normalisation beyond whitespace rejection).

### FR-003 — Short code generation
Codes are generated server-side; the caller cannot choose them in this release (see OQ-004).
- Acceptance criteria:
  - Each code matches `^[A-Za-z0-9]{7}$`.
  - Codes are generated with a cryptographically secure source and are unique among links currently stored.
  - Two creations for the same `long_url` return two distinct codes, both resolving to that URL (no de-duplication; see OQ-007).
  - A collision with an existing code triggers regeneration; the caller never receives an existing code.

### FR-004 — Resolve and redirect
`GET /{code}` redirects to the stored long URL.
- Acceptance criteria:
  - An existing code returns HTTP `302` with a `Location` header exactly equal to the stored `long_url`.
  - The response has no body requirement beyond an optional short text/HTML notice.
  - The redirect response carries `Cache-Control: no-store` so intermediaries do not suppress click counting.
  - Options (`OPTIONS`) and other methods on this path return HTTP `405`.

### FR-005 — Click counting
Each successful redirect increments the link's click count.
- Acceptance criteria:
  - A fresh link reports `clicks = 0` before any redirect.
  - After exactly three successful redirects the link reports `clicks = 3`.
  - A request for an unknown code increments nothing and returns HTTP `404`.
  - `GET /links/{code}/stats` calls never change `clicks`.
  - Concurrent redirects to the same code are all counted (no lost updates).

### FR-006 — Link statistics
`GET /links/{code}/stats` returns the click count for a code.
- Acceptance criteria:
  - An existing code returns HTTP `200` with JSON `code`, `long_url`, `clicks` (integer ≥ 0), `created_at`, and `last_clicked_at` (ISO-8601 UTC timestamp or `null` when never clicked).
  - The response reflects all redirects that completed before the stats request.
  - An unknown code returns HTTP `404` with `error.code = "not_found"`.
  - Codes are case-sensitive: a code differing only in letter case is unknown and returns `404`.

### FR-007 — Unknown code handling
Requests for codes that were never issued or are no longer stored must not redirect.
- Acceptance criteria:
  - `GET /{unknown}` returns HTTP `404` and no `Location` header.
  - Characters not allowed by the code pattern (e.g. `a.b`, `a%20b`, `a/b`) return HTTP `404` or `422`, never a redirect.
  - A 404 response never redirects to the submitted value (no open redirect).

### FR-008 — Reserved paths and routing precedence
Fixed API routes must not be shadowed by the code route.
- Acceptance criteria:
  - Codes are never generated for, and `POST /links` never returns, the reserved path segments `links`, `health`, `docs`, `redoc`, `openapi.json`.
  - `GET /health` returns HTTP `200` with `{"status": "ok"}`.
  - `GET /docs` and `GET /openapi.json` remain available and serve the API documentation.

### FR-009 — Error response format
All non-2xx/3xx API responses (except framework-generated validation errors, which must be normalised where practical) use one JSON envelope.
- Acceptance criteria:
  - Body shape is `{"error": {"code": "<machine_code>", "message": "<human readable>"}}`.
  - `code` is one of `invalid_url`, `invalid_request`, `not_found`, `method_not_allowed`, `internal_error`.
  - `message` is non-empty and contains no stack trace, file path, or internal identifier.
  - Every documented error status in this FSD is asserted by at least one test.

### FR-010 — Request limits
The service bounds request size and rejects unexpected payloads.
- Acceptance criteria:
  - A request body larger than 64 KiB is rejected with HTTP `413` and no link is created.
  - Unknown JSON fields in `POST /links` are ignored (they do not cause an error).
  - The documented maximum `url` length (2048 characters) is enforced independently of body size.

### FR-011 — Idempotency and repeated submissions
Behaviour for repeat submissions of the same URL is explicit.
- Acceptance criteria:
  - Submitting the same `url` twice returns HTTP `201` twice with different `code` values.
  - Both links are tracked and counted independently.

### FR-012 — Stateless-external behaviour and restart
In-memory storage behaviour is explicit and testable.
- Acceptance criteria:
  - All data is lost on process restart; after restart a previously issued code returns HTTP `404`.
  - Behaviour is defined for a single process only; the spec assumes one Uvicorn worker (see OQ-009).

### FR-013 — Automated acceptance tests
Every functional requirement above is covered by pytest tests using httpx/TestClient against the real application object.
- Acceptance criteria:
  - Each FR has at least one test whose name references the FR id.
  - Tests share no global state: storage is reset between tests via a fixture.
  - The suite runs offline (no real external network calls) and passes with `pytest -q`.
  - Tests cover the happy path, each rejection case in FR-002, unknown codes, and concurrent click increments.

## Non-Functional Requirements

| ID | Requirement |
|---|---|
| NFR-001 | Latency: p95 ≤ 50 ms per request for a single local process with 10,000 stored links; stats lookups are O(1) average. |
| NFR-002 | Correctness under concurrency: click increments are atomic and never lost for 100 parallel redirects to the same code. |
| NFR-003 | Capacity: at least 100,000 links in ≤ 256 MB RSS; no unbounded growth of per-request state. |
| NFR-004 | Security: only `http`/`https` targets are accepted (blocks `javascript:`/`data:` redirect abuse); no open redirect; error bodies leak no internals. |
| NFR-005 | Privacy: logs record code, method, path, status and timing; full `long_url` values and client IPs are not logged at INFO (see OQ-013). |
| NFR-006 | Observability: `GET /health` returns `200` when the process can serve requests; startup/shutdown and errors are logged with a request id. |
| NFR-007 | Maintainability: typed request/response models (Pydantic) and OpenAPI schema generated by FastAPI; no dead endpoints. |
| NFR-008 | Portability: Python 3.12, dependencies limited to FastAPI, Uvicorn, Pydantic, pytest, httpx; no external database or network dependency at runtime. |
| NFR-009 | Determinism: timestamps are UTC ISO-8601 with `Z`/`+00:00`; tests do not depend on wall-clock values beyond format and ordering. |

## Assumptions

- A1: The service is consumed as a JSON API by tools or humans; no HTML UI is required. The stack permits static HTML, which is not needed for this story.
- A2: `short_url` is built from a configured base URL (e.g. `http://localhost:8000`) supplied by environment variable `BASE_URL`, defaulting to the request's base URL in development.
- A3: Redirect status is `302 Found` (temporary) so that click counting stays meaningful; see OQ-006.
- A4: Only one process/worker runs, so a plain in-memory dict guarded by a lock is sufficient.
- A5: No authentication, authorisation, rate limiting, or per-user ownership is required in this release (OQ-011, OQ-012).
- A6: Codes are case-sensitive, 7 characters, base62, generated with `secrets`.
- A7: "Click count" means the number of successful redirect responses served, not unique visitors.
- A8: URLs are stored as submitted after validation; no canonicalisation, tracking-parameter stripping, or malware/safe-browsing check.
- A9: Statistics are available only for codes that currently exist; there is no historical retention after deletion or restart (no delete endpoint exists).
- A10: Any UI deliverable is out of scope, so the "static HTML" option in the stack is unused.
